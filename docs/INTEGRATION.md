# Integrating with TensorPit

**For developers.** This is how a program drives TensorPit: how a research report becomes a sealed
campaign, how a campaign is simulated, and how — where the deployment allows it — a person starts it
trading. If you are connecting Claude rather than writing code, read
[connect.md](../plugins/prostocks/skills/prostocks-campaign/references/connect.md) instead; if you are
writing the report itself, read [STRATEGY-INSTRUCTIONS.md](STRATEGY-INSTRUCTIONS.md).

Every tool named here is listed with its arguments in [TOOLS.md](TOOLS.md). To run TensorPit on your
own machine while you build a client against it, see [§9](#9--running-tensorpit-on-your-own-machine).

---

## 1 · The shape of it

TensorPit is **two MCP servers**, and a REST API that does the same work.

| | path | what it owns |
|---|---|---|
| **compiler** | `/api/v1/mcp/compiler` | a report becomes a campaign: submit, correct, accept the reading, finalize |
| **runner** | `/api/v1/mcp/runner` | a sealed campaign runs: simulate, and (where enabled) trade |
| **both** | `/api/v1/mcp` | every tool above, on one connection — the address a person is given |

⛔ The address is not the gate. What a credential may reach is its SCOPE (below), identical on all
three; a token, though, is bound to the address it was minted for, so each is its own grant.

Both are OAuth 2.1 protected resources with one authorization server in front of them. **Each is
consented separately** — a token for one is not a token for the other.

Three rules hold everywhere, and knowing them saves a day of debugging:

- ⛔ **TensorPit never calls you.** There are no webhooks. You poll (`get_*`) or you hold a long poll
  open (`watch_*`). A 2026-07-28 MCP client may also subscribe to a compilation resource and be told
  when it moves, but reading it is still your call.
- ⛔ **A tool you cannot use is not registered.** Profile, deployment flag and key scope decide which
  tools exist for your credential; they never make a tool answer "no". If `start_trading` is missing
  from `tools/list`, trading is off for you. Always read `tools/list` (or `get_capabilities`) rather
  than assuming.
- ⛔ **Nothing you do here places an order** except `start_trading`, and that takes two calls with a
  person's confirmation between them. Compiling, correcting, accepting a reading, finalizing and
  simulating never touch a broker.

### Who you are: the profile

`get_capabilities` (compiler) and `get_runner_capabilities` (runner) report a `plugin` block whose
`profile` TensorPit derives from your credential — you configure nothing:

```jsonc
{ "profile": "consumer",   // a person is here: an OAuth grant, or a signed-in session
  "flowEnabled": true,
  "simulate": true,        // consumer only
  "trade": false,          // consumer only, and off unless the deployment turned it on
  "engineChoice": false }
```

`pipeline` arrives on a service key — nobody is there to ask. The difference is not cosmetic:

| | `consumer` | `pipeline` |
|---|---|---|
| who accepts the reading | **the person**, with `confirm_reading` | accepted automatically |
| who answers the compiler's questions | the person, through `answer_questions` | you, in the report or an answer |
| simulation | yes, with the person's capital and paths | ⛔ never — the capital and the paths are a person's to choose |
| trading | only where the deployment enabled it, confirmed per start | ⛔ never |

### Keys and scopes

Mint a key in the TensorPit webapp (**Settings → API Keys**); the plaintext is shown once. A key acts
as the user who minted it, and key management is first-party only — there is no API for it.

A key carries a **scope**:

- `full` — everything its owner can do, both surfaces.
- `reports` — the report loop and read-only compilations, on the **compiler surface only**. It reaches
  no runner tool, no simulation, no live session.

A call outside your scope answers **403 `out_of_scope`** — never 401. A 401 would tell you to retry
something that can never work. On MCP, a narrow key simply sees fewer tools.

## 2 · The report loop

One `strategy_id`, generated by TensorPit, identifies a strategy for its whole life. ⛔ You never
choose it; sending one is a 400.

```
submit_report ──▶ strategy_id
      │
      ▼
get_compilation / watch_compilation   ◀── poll or long-poll
      │
      ├── pending                 the model is working; keep watching
      ├── corrections_required    issues to fix: revise_report, refine_report, or answer_questions
      ├── awaiting_confirmation   the reading is ready — a person accepts it (confirm_reading)
      ├── accepted                the campaign is SEALED; it can be simulated
      ├── finalized               the report text is frozen
      └── failed                  the error is on the view
```

### Submitting

```jsonc
// submit_report
{ "report": "# HOOD — …",   // markdown prose about ONE ticker
  "ticker": "HOOD",          // optional: the compiler reads it from the report if you leave it out
  "title": "Stand aside into Q3" }
```

⚠️ **The answer is camelCase.** `submit_report` answers the intake's own object, not one of the
snake_case views the other tools return:

```jsonc
{ "strategyId": "4fcb1c35-…", "ticker": "HOOD", "created": true,
  "status": "queued", "checks": [ { "code": "TP-W-INTAKE-PULSE", "message": "no market pulse. …" } ],
  "createdAt": "2026-10-21T22:37:15.115Z" }
```

`checks` are advisory: the report is stored whatever they say. Only something that is not a report at
all is refused — empty, under 400 characters, over 1 MiB, or not about one ticker.

### Submitting the same text twice

A retry is safe and never files twice. The same bytes from the same submitter answer `status:
"duplicate"` with the id already issued, where it stands, and the question to put to a person:

```jsonc
{ "strategyId": "a1c79cdb-…", "created": false, "status": "duplicate",
  "seenBefore": { "strategyId": "a1c79cdb-…", "status": "accepted",
                  "submittedAt": "2026-10-21T18:52:00Z", "compiledAt": "2026-10-21T20:03:48Z", "copies": 1 },
  "ask": "I've seen this report already … Do you want to compile it again?" }
```

⛔ Do not swallow `ask`. A person is entitled to both answers:

- **carry on with the earlier one** — use `seenBefore.strategyId`; nothing is compiled, nothing is charged;
- **compile it again** — submit the same text with `compile_again: true`. That makes a **new strategy**
  from the same text, compiled from scratch, with every question asked afresh; the earlier one is
  untouched.

A pipeline with nobody to ask carries on with the earlier one.

### Correcting

Three ways, and the difference matters:

| | what it does | when |
|---|---|---|
| `revise_report` | replaces the report text under the same `strategy_id` | the report itself was wrong |
| `refine_report` | files **one instruction** on top of the report; it supersedes the report, and every earlier instruction, where they conflict | one thing should change and you would rather not rewrite |
| `answer_questions` | answers the compiler's `TP-Q-REPORT-*` questions in the person's own words | the report cannot say it — a date only the author knows, a choice between two readings |

Answers become part of the source and **survive a revision**. A revision may not take text another of
your strategies already holds (409 `report_text_taken`).

### Reading where it stands

`get_compilation` returns one object for an author. Two fields are for different readers and you
should not mix them up:

- `issues[]` — for your program: `code`, `pointer`, `problem`, `expected`, and `question_id` on a
  question. Each issue also carries **`plain`** (one sentence), its report **`section`** and the
  **`quote`** it came from.
- `summary` — for the person reading the transcript.

⛔ Show a person `plain`, never `code` or `pointer`. The codes name bands, rosters and executors; the
plain sentence is written for someone who has never seen the inside of the compiler.

While `awaiting_confirmation`, the view also carries the **`reading`** whole — how TensorPit read the
strategy, every value quoted from the author's own words — with the `ast_digest` that accepts it.

### Following a compile live

`watch_compilation` is the same data as `get_compilation` plus the compile's own events after a
cursor, and it **holds the request open** (up to 25 s) while the compile is running:

```jsonc
// watch_compilation { "strategy_id": "…", "cursor": 0, "wait_ms": 20000 }
{ "strategy_id": "…", "cursor": 152, "more": true,
  "events": [ { "seq": 1, "at": "…", "type": "received", "ticker": "HOOD" },
              { "seq": 2, "at": "…", "type": "round.started", "round": 1 },
              { "seq": 3, "at": "…", "type": "reasoning.delta", "round": 1, "text": "…" } ],
  "view": { "status": "pending", … } }
```

Loop: pass the `cursor` you were given back on the next call. **`more: true` means ask again at once**
rather than waiting — the answer was trimmed to fit. A compile is typically one model round of one to
three minutes, and most events are `reasoning.delta` — the model thinking aloud. Show a person a line
of status and an elapsed clock, not 150 raw events.

Event types: `received`, `ticker.named`, `calendar.looked_up`, `round.started`, `reasoning.delta`,
`answer.delta`, `round.answered`, `round.retried`, `checked`, `repair`, `questions`, `reading.ready`,
`reading.confirmed`, `answered`, `outcome`.

### Accepting the reading — the gate

⛔ **A compile that passes seals nothing.** It stops at *here is how I read your strategy*. For a
`consumer`, the campaign exists only once a person accepts that reading:

```jsonc
// confirm_reading
{ "strategy_id": "…", "ast_digest": "0c7cd6bc…" }   // exactly as get_compilation gave it
```

A digest that is no longer current is refused (`reading_stale`) — re-read the compilation and show the
person the new reading. For a `pipeline`, this already happened; the view goes straight to `accepted`.

⛔ Confirming is not finalizing. **Confirm accepts a reading; finalize freezes the text.** Between the
two, the campaign exists and can be simulated while the report is still yours to revise.

### What the campaign actually does

Once sealed, `get_compilation` carries **`campaign_summary`**: a few plain sentences written from the
plan that will run — the entry and the stop that run, each event's reaction — not from the report's
words. Show it to a person before they simulate, and again before they finalize. It is the honest
answer to "what did you build from what I wrote?".

### Finalizing

`finalize_report` freezes the text: no more revisions. The campaign was already sealed at
confirmation. ⛔ Finalizing does not start trading, and a program should not finalize on a person's
behalf without asking — it removes their ability to correct the report.

A revision, refinement or finalize on a deleted report is refused with **410 `report_deleted`**.

### Rate

A compile may be rationed per person per UTC day. Spent answers **429 `compile_limit_reached`** with
`Retry-After` — never 403, because the allowance comes back. A resubmission of bytes already filed and
a revision that changes nothing compile nothing and are free; "compile it again" is a compile and
counts.

## 3 · Simulation — testing the machinery

⛔ **A simulation is never evidence of edge, and never a reason to go live.** It runs the campaign on
futures built from the report's own scenarios to see whether the machinery finds them, enters, sizes,
stops and exits as the report means. Every TensorPit surface says so, and so should yours.

Simulation is the **runner's** surface, and a `consumer` tool: the capital and the paths are a
person's to choose, so a pipeline never simulates.

### 1. Propose the paths

```jsonc
// propose_simulation_paths { "strategy_id": "…" }     — nothing runs
{ "strategy_id": "…", "ticker": "HOOD", "start_day": "2026-10-22", "covered": 0.835,
  "calibration": { "start_price": 101.94, "daily_vol_pct": 2.4, "typical_gap_pct": 6 },
  "paths": [ { "id": "range-hold--range-holds", "kind": "probable", "probability": 0.225,
               "outcome": "stalls", "story": "range hold, range holds (stalls; 22.5% of the report's odds). …" } ] }
```

The paths are the scenarios' own odds — each scenario's prior times each trajectory's probability, most
probable first, until about 80% of the odds are covered — plus **one risk path**: the likeliest path
that engages the campaign, then a gap through its stop. `probability: null` marks it. No model is
involved; these are the report's numbers.

Show the person the stories, let them pick, and ask for the capital. ⛔ Never default the capital.

### 2. Run it

```jsonc
// run_simulation { "strategy_id": "…", "cash": 100000, "path_ids": ["range-hold--range-holds", …] }
{ "simulation_id": "53af4b76-…", "status": "running", "cash": 100000, "paths": [ … ] }
```

It answers at once and the paths run behind it — **minutes a path**. Each path is first tuned with no
model call until the campaign's own scenario tracking recognises the path it means (pushed harder up
to three times), then traded by the campaign's own Campaign Manager.

### 3. Follow it

`watch_simulation` is `watch_compilation`'s twin — the same `{ events, cursor, more, view }`, the same
long poll, the same `more` rule:

```jsonc
{ "simulation_id": "…", "cursor": 22, "more": false,
  "events": [ { "seq": 2, "type": "path.started", "path_id": "…", "index": 1, "of": 6, "story": "…" },
              { "seq": 3, "type": "tuning.started", "path_id": "…", "strength": 1, "attempt": 1, "of": 3 },
              { "seq": 10, "type": "tuning.checked", "path_id": "…", "strength": 1, "recognised": false },
              { "seq": 16, "type": "progress", "path_id": "…", "phase": "run", "elapsed_ms": 3000 },
              { "seq": 21, "type": "path.done", "path_id": "…", "engaged": false, "fills": 0 } ],
  "view": { … } }
```

`progress` is a heartbeat every few seconds while a step is in flight: it carries **time only**, so a
long step never looks like a hung one. The news is always the milestone beside it. Event types:
`started`, `path.started`, `tuning.started`, `tuning.checked`, `run.started`, `progress`, `path.done`,
`path.failed`, `outcome`.

`get_simulation` gives the same view without the events, and `list_simulations` gives a strategy's.

### 4. Read what it found

Per path: whether the campaign **engaged**, its fills, return, worst drawdown, whether the stop held,
the decisions that changed something, and its model calls. Across the paths, the return weighted by the
report's own odds.

Two findings matter more than the numbers, and a good integration surfaces both:

- **`recognised: false`** — the campaign's own scenario tracking never recognised a path built from its
  own scenario, even pushed harder. That is a finding about the report's gates, not about the run.
- **`engaged: false`** — the campaign never entered on that path. ⛔ This is *not* a 0% result. Draw it
  as "it never entered", never as a zero bar: a flat trade and a trade that never happened are
  different facts, and conflating them hides the interesting one.

## 4 · Live trading

⛔ **Trading is the runner's, a person's, and off unless the deployment turned it on.** If
`list_trading_accounts` and `start_trading` are absent from `tools/list`, this deployment does not
offer them to you — that is the answer, and there is nothing to retry.

⛔ **Stopping a session is not on this API.** It stays in the TensorPit webapp, with the account owner.
Do not build a product that can start something it cannot stop; say where the stop is.

### The two-call start

`list_trading_accounts` gives the brokerage accounts linked in TensorPit (name, institution, masked
number). Ask the person which one — never pick.

**Call one, without `confirm_token`:** nothing starts. You get exactly what would start, the campaign's
own summary, and a token good for five minutes, bound to you, the strategy, the account and the capital.

```jsonc
// start_trading { "strategy_id": "…", "account_id": "…", "cash": 25000 }
{ "started": false,
  "would_start": { "ticker": "HOOD", "slug": "hood-s4fcb1c35-…", "account": { … }, "cash": 25000 },
  "campaign_summary": [ "Trades HOOD long only (a bet on a rise), and ends in cash.", … ],
  "confirm_token": "…", "expires_in_s": 300,
  "summary": "Would start trading HOOD … LIVE … It places orders with the broker. …" }
```

**Read that to the person.** Only when *they* say yes, call again with the token. A token minted for
another strategy, account or amount — or an expired one — is refused; ask again rather than reusing one.

**Call two** answers the session: `session_id`, `status`, `symbols`, `cash` (initial and current),
`positions`, `unrealized_pnl`, `failure_reason`. `get_trading_session` reads it back later.

Prerequisites, so you can fail early with a clear message: the campaign must be **sealed** (a
confirmed reading — `accepted` or `finalized`), not archived, and the account must be linked in
TensorPit.

## 5 · The runner, and what a sealed campaign is

A sealed campaign is identified by the **`strategy_id`** the compiler gave you. There is no other
handle: the runner takes `strategy_id` everywhere, resolves it to the campaign that strategy compiled
into, and refuses what is not sealed with `not_compiled`.

What the runner guarantees, and why a start can be refused for reasons that have nothing to do with
your request:

- A campaign runs **exactly what was sealed**. The runner never recompiles, never edits a plan and
  never substitutes a default for something it cannot run.
- Before anything starts, the sealed bundle is **verified against this deployment** — its hash, its
  schema, every unit and executor it names, and the safety invariants re-checked against the capital.
  A bundle this deployment cannot run is refused with every reason named (`bundle_not_loadable`).
- Every symbol it needs is **checked at the market-data vendor** first; a name the vendor has nothing
  for is refused (`data_not_provisionable`) rather than run blind. A simulated run asks no vendor.

A campaign is archived or deleted by its owner, in TensorPit. An archived campaign refuses a new run;
deleting takes the campaign and its data together, and is refused while anything of its own is active.

## 6 · The same work over REST

Every MCP tool above is a thin wrapper over one service, and that service also answers REST. Use REST
if you are a pipeline and would rather not speak MCP. Authenticate with your key as a bearer token.

| what | REST |
|---|---|
| submit a report | `POST /api/v1/reports` |
| where a compile stands | `GET /api/v1/reports/{strategyId}/compilation` |
| revise · refine · finalize | `POST /api/v1/reports/{strategyId}/{revise,refine,finalize}` |
| a report, and the list | `GET /api/v1/reports/{strategyId}` · `GET /api/v1/reports` |
| the simulation paths | `POST /api/v1/simulations/proposal` |
| run a simulation | `POST /api/v1/simulations` |
| follow one · read one · list | `GET /api/v1/simulations/{id}/events` · `GET /api/v1/simulations/{id}` · `GET /api/v1/simulations?strategyId=…` |
| where to find the MCP surfaces | `GET /api/v1/mcp-host` |

`GET /api/v1/simulations/{id}/events` is the same contract as `watch_simulation` —
`{ events, cursor, more, view }`, with `after` and `wait_ms` as query parameters — so a REST client gets
the same live view an MCP client does.

`GET /api/v1/reports` narrows on `submittedBy` and `status`, which is how a provider imports one
person's finished strategies (`?submittedBy=<sub>&status=finalized`). ⚠️ `submittedBy` is the server's
own record of who filed it; `author` is free text a caller supplied and proves nothing.

Starting a live session over REST is the account owner's step in the webapp, not an integration path.

## 7 · Refusals worth handling

Every refusal carries a `code` and a sentence. These are the ones an integration meets:

| code | status | what it means |
|---|---|---|
| `out_of_scope` | 403 | your key's scope does not reach this. Not retryable |
| `compile_limit_reached` | 429 | today's compiles are spent; `Retry-After` says when |
| `report_deleted` | 410 | the report went with its compilation; submit it again to start over |
| `report_text_taken` | 409 | another of your strategies already holds that text |
| `reading_stale` | — | the reading moved under you; re-read it and show the person the new one |
| `report_not_found` | — | no such strategy **for you**. Someone else's reads exactly like an unknown one |
| `not_compiled` | 409 | the campaign is not sealed yet: its reading must be accepted first |
| `campaign_archived` | 409 | restore it in TensorPit to run it |
| `bad_cash` · `no_paths` · `no_history` | 422 | the capital was not above zero · none of those path ids is proposed · the name has no real history to build paths from |
| `bundle_not_loadable` · `data_not_provisionable` | 422 | this deployment cannot run that sealed campaign · the vendor has nothing for a symbol it needs |
| `simulation_not_found` · `account_not_found` · `confirm_token_invalid` | — | as named; mint a fresh token by calling `start_trading` without one |

⛔ **Ownership is silent.** Every report and simulation tool acts only on your own; someone else's id
answers exactly as an unknown id does. Never infer existence from a refusal.

## 8 · Versions, and what will not move under you

- The skills and these guides are **generated from TensorPit** and published here; releases are
  tagged, and `VERSION.json` names the contract version and the commit they were built from. Pin a tag
  and record it with each run.
- The report discipline is served live as `get_strategy_instructions` on the compiler surface. Read it
  at the start of a session rather than caching a copy: it is the same text this repository publishes,
  but the live one is always the deployment's own.
- Tool names and the shape of what they answer are the contract. A new field may appear; read
  defensively and ignore what you do not know. Read `tools/list` rather than hard-coding which tools
  exist — that is how a deployment tells you what it offers you.

## 9 · Running TensorPit on your own machine

For developing a client against a TensorPit you run yourself. This setup has **no sign-in, no database
server and no Redis**: a request without a credential is treated as one person, `owner`, which is what
makes the person-only tools — answering questions, accepting a reading, simulating, deleting — available
to a local client. Every step below was run end to end; the table at the bottom is what each missing
piece looks like when it is missing.

### 1 · Check out, and install every time you pull

```bash
git pull && pnpm install
```

⚠️ `./start.sh` installs dependencies only when `node_modules` is **missing**. A checkout that has fallen
behind keeps its old `node_modules`, builds against stale dependencies, and fails. Node 20 or later, pnpm
10 or later.

### 2 · `tensorpit/.env`

```bash
FUSIONAUTH_ENABLED=false
TENSORPIT_DEV_PROFILE=consumer
RUNNER_ISOLATION=worker-thread
FIREWORKS_API_KEY=<your Fireworks key>
TENSORPIT_DATA_VENDOR=massive
MASSIVE_API_KEY=<your Massive key>
```

| line | why it is there |
|---|---|
| `FUSIONAUTH_ENABLED=false` | the API's sign-in is **on** by default — and TensorPit refuses to start with the dev profile while it is |
| `TENSORPIT_DEV_PROFILE=consumer` | a request with no credential is a person (`owner`). Without it a local client is a `pipeline`, and the person-only tools are not registered for it |
| `RUNNER_ISOLATION=worker-thread` | ⚠️ unset, a simulation's runs execute on the API's own thread and block it for minutes — both MCP servers stop answering in the middle of a simulation |
| `FIREWORKS_API_KEY` | the compiler's model; without it the compiler is off and no report ever compiles. The default model is `deepseek-v4p1-flash` — set `FIREWORKS_MODEL` to change it everywhere, or `TENSORPIT_COMPILER_MODEL` for the compiler alone |
| `TENSORPIT_DATA_VENDOR` and its credentials | a simulation builds its paths from about fourteen months of the ticker's **real** daily bars and warms up on real bars, so with no vendor `propose_simulation_paths` answers `no_history`. Unset, the vendor is `massive`. The others: `alpaca` (`ALPACA_API_KEY_ID`, `ALPACA_API_SECRET_KEY`) or `marketstore` (`MARKETSTORE_URL`, `MARKETSTORE_API_KEY`, `CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET`) |

Worth adding:

| line | what it buys |
|---|---|
| `FMP_API_KEY`, `FMP_PLAN=premium` | the compiler looks up the ticker's scheduled earnings date itself instead of asking the author for it |
| `TENSORPIT_MCP_STATE_SECRET` | 32 or more random bytes. Without it a confirmation or a question round minted before a restart is refused after it |
| `TYPESAFE_API_KEY` | **only** if you choose the JEV Campaign Manager. A report campaign runs QuantCM by default, which asks no model |

Not needed: `REDIS_URL`, `DATABASE_URL`, `TENSORPIT_PUBLIC_URL`, `TENSORPIT_MCP_HOST_ORIGINS` (the Apps'
sandbox already accepts any `localhost` or `127.0.0.1` page), or any OAuth setting. There is no compile
limit unless you set `TENSORPIT_COMPILES_PER_USER_PER_DAY`.

### 3 · `webapp/.env.production.local`

```bash
VITE_FUSIONAUTH_ENABLED=false
VITE_FUSIONAUTH_CLIENT_ID=
```

⚠️ TensorPit's own webapp has its sign-in **baked in when it is built**, separately from the API's. Without
this file it sends you to a sign-in page you cannot use locally. Your MCP client does not need it;
TensorPit's webapp does. `./start.sh` rebuilds the webapp, so the file takes effect on the next start.

### 4 · Start it

```bash
./start.sh
```

It serves on **:4317** — the API, both MCP servers and TensorPit's webapp — and the MCP Apps' sandbox on
:4318. The start banner prints both MCP addresses. The database is embedded and lives in the checkout.

`./start.sh --local` instead starts Postgres and Redis in Docker (on 5433 and 6380). You need it only for
live sessions; leave it off if anything else on your machine holds those ports.

### 5 · ⛔ Do not mint an API key locally

One API key — or `TENSORPIT_API_TOKEN` — makes TensorPit demand credentials on **every** request, and a key
makes its caller a `pipeline`: the dev profile applies only to requests that carry no credential. If you
minted one before, delete it in the webapp (**Settings → API Keys**).

### 6 · Check

- Connect your client to `http://localhost:4317/api/v1/mcp` (or a single component, `…/mcp/compiler` and `…/mcp/runner`) with **no
  credential**. TensorPit binds `127.0.0.1`; if `localhost` does not connect, use `127.0.0.1`.
- `get_capabilities` and `get_runner_capabilities` both report `plugin.profile: "consumer"` and
  `simulate: true`.
- TensorPit's webapp at `http://localhost:4317` acts as the same `owner`, so a report your client submits
  is the same person's there and appears in its **Compilations** list.

What does not work locally: **live trading** — with no Redis no live session can start, and the server
says so at boot — and anything that needs a real sign-in.

### When something is off

| you see | the cause |
|---|---|
| `profile: "pipeline"` | an API key exists, or `TENSORPIT_DEV_PROFILE` is missing |
